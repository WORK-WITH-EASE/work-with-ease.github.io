# Projekt und Zusammenarbeit

Wir entwickeln mit Andrea die Homepage von **Work with Ease**: Prozesse zuerst vereinfachen, dann sinnvoll digitalisieren und KI im Arbeitsalltag einsetzen. Ziel ist produktiveres, zufriedeneres Arbeiten. Die statische Website wird über GitHub Pages unter `work-with-ease.com` veröffentlicht; das Repository ist öffentlich.

- Auf Deutsch arbeiten. Die bestehende Website im Repository ist der gemeinsam erarbeitete Stand und wird schrittweise weiterentwickelt. Bei reinen Planungsfragen nicht ungefragt Code ändern.
- **Website-Code und benötigte Assets gehören von Anfang an ins Git-versionierte Repository:** Bearbeitbare HTML-Vorlagen unter `src/`, gemeinsame Bausteine unter `src/_includes/`, Navigation/Kontaktdaten unter `src/_data/`, CSS/JavaScript unter `src/static/`; Bilder und Schriften unter `assets/`. `npm run produce` erzeugt daraus die fertigen HTML-/CSS-/JS-Dateien im Root. Root-Ausgabedateien nicht direkt bearbeiten; Quellen UND Ausgabe gemeinsam committen. Auch unfertige Entwicklungsstände werden versioniert. Keine Website, Prototypen oder benötigten Assets in `.planning/` oder anderen durch `.gitignore` ausgeschlossenen Bereichen entwickeln.
- **Nur Dokumentation, Ideen und Gesprächsnotizen** gehören in `.planning/`. Dieser Ordner bleibt lokal und wird nicht committed. Private Ausgangsmaterialien nicht ungeprüft ins öffentliche Repository übernehmen.
- Sinnvolle Zwischenstände selbstständig und regelmäßig committen; nicht erst die fertige Website. Vor Abschluss einer Änderung den Git-Status prüfen und zugehörige Dateien berücksichtigen.
- **Standardmäßig direkt auf `main` arbeiten, auch bei größeren Änderungen. Neue Branches ausschließlich auf ausdrücklichen Wunsch von Andrea anlegen; niemals eigenständig.** Zu Sessionbeginn den tatsächlichen Branch prüfen. Kleinschrittige Commits und `produce` selbstständig durchführen. Falls ausdrücklich auf einem Branch gearbeitet wird, nicht ohne Auftrag nach `main` mergen.
- **Nur auf ausdrückliche Anweisung von Andrea pushen.** Ein normaler Push-Auftrag betrifft den auf `main` zusammengeführten Stand; Entwicklungsbranches nicht eigenständig pushen. Liegen gewünschte Änderungen noch auf einem Branch, die Zusammenführung vor dem Push klären.
- Bei jedem ausdrücklich beauftragten Veröffentlichungs-Push den letzten zu veröffentlichenden Commit mit einem annotierten Versions-Tag markieren und genau diesen Tag zusammen mit `main` pushen (nach Möglichkeit atomar). Vorher vorhandene Remote-Tags prüfen. Schema `v1.0.0`, danach standardmäßig die letzte Zahl erhöhen (`v1.0.1` usw.), sofern Andrea keine andere Version vorgibt. Tag-Nachricht mit Datum und kurzer Änderungsbeschreibung; bestehende Tags niemals verschieben oder überschreiben. Erfolg von Branch- und Tag-Push prüfen. Ein Tag markiert den veröffentlichten Git-Stand, nicht den bestätigten Abschluss des GitHub-Pages-Deployments.
- Vor Commits `npm run produce` und `npm run check` ausführen. Nach Änderungen an Vorlagen oder Generator passende Funktionsprüfungen durchführen. Automatisches Erzeugen während der Arbeit: `npm run dev`. Nach Installation auf einem neuen Rechner zuerst `npm ci`.
- Vorschau mit `python3 scripts/serve.py` auf **http://localhost:4000**. Sie liefert die Website direkt aus dem Repository-Root und zeigt den ausgecheckten Stand. Keine separate Vorschau-Kopie pflegen.
- `CNAME` erhalten. Offene Inhalte oder Platzhalter nicht durch erfundene Angaben ersetzen.
- SEO und Auffindbarkeit in KI-Suchen fortlaufend berücksichtigen. Vor relevanten Entscheidungen aktuelle offizielle Quellen prüfen, konkrete Verbesserungen vorschlagen und Anforderungen von Empfehlungen bzw. Annahmen unterscheiden. Prüfdatum, Quellen und offene Punkte in `.planning/` dokumentieren; keine Ranking- oder Zitierungsgarantien versprechen.
